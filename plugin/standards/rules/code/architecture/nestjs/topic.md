# NestJS Architecture

How the base rules apply to a NestJS application. Two kinds of statement, each
labeled by what it is:

- **Mandated** — what NestJS resolves or requires: kebab-case filenames
  throughout (`events.service.ts`, `create-event.dto.ts`), and `src/main.ts`
  as the bootstrap entry its CLI resolves. These facts live in the framework
  carve-out table, which the checks consult — this document refers to them and
  never restates them as rules.
- **Applied** — how the base rules read against Nest code. Everything below
  cites the base rule it applies; none of it overrides one.

**Classes are criterion d, not an exception.** Nest's dependency injection
requires classes for services, controllers, resolvers, guards, pipes and
interceptors — that is exactly criterion d of the
[class bright-line](../../style-guide/patterns/classes/05-class-bright-line/rule.md).
A class Nest does not require still needs one of the other criteria; "it's a
Nest project" earns nothing by itself.

**Decorated classes are framework-owned for the class rules.** Extending a
Nest-provided base or implementing its interfaces is the framework's contract,
per the carve-out in
[class inheritance](../../style-guide/patterns/classes/30-class-inheritance/rule.md).
Sharing between your *own* classes still composes — hold a collaborator and
delegate — exactly as that rule states.

**Constructor-injected types are value imports.** Nest reads injection tokens
from decorator metadata, so a type used in a decorated class's constructor
must not be imported with `import type` — the
[type-only import rule](../../style-guide/conventions/lint-and-formatting/10-import-type-only/rule.md)
carves this out; everywhere else in a Nest file, type-only imports stay
type-only.

**Modules and folders are ordinary.** A Nest module is wired by decorators
(`@Module`), not by folders — so folder layout follows the base rules
unchanged: features grow by the
[domain-folder rule](../folder-structure/55-ungrouped-domain-utils/rule.md), shared
code lands by the [placement rule](../folder-structure/05-shared-code-placement/rule.md),
and `controllers/`, `services/` and their siblings are legal folder names
everywhere without declaring anything (the
[banned-folder-name rule](../folder-structure/25-banned-folder-name/rule.md)
bans junk drawers, not framework vocabulary). The suffix convention
(`*.service.ts`, `*.controller.ts`, `*.module.ts`, `*.guard.ts`, `*.dto.ts`)
is Nest's own documented naming, generated by its CLI — follow it; the
[filename-match rule](../../style-guide/conventions/file-naming/05-filename-mismatch/rule.md)
already reads those dotted kebab names as the framework's.
